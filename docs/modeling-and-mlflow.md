# Reproducible modeling and local MLflow

## Implemented workflow

From the repository root, using the Python 3.11 virtual environment:

```powershell
.\.venv\Scripts\python.exe -m src.models.train compare
.\.venv\Scripts\python.exe -m src.models.train finalize
```

Run these in sequence after discovery and preparation. `compare` opens only
training and validation example files. It fits two deterministic historical
baselines, Ridge, and a random forest using `configs/training.json`, then writes
`models/selection.json` and `reports/model-comparison.json`.

`finalize` checks that training code, configuration, dependencies, and the
preparation report have not changed since selection. It refits the selected
approach on training plus validation and verifies serialization predictions.
Before opening the test example file, it writes a persistent evaluation marker.
It then evaluates the selected final model on test data and saves the results.

Once the marker exists, further comparison and finalization commands are blocked
in that workspace. This is a workflow guard, not a security boundary. A fresh
checkout and data preparation can reproduce the experiment without deleting
or silently overwriting the recorded test event. If final evaluation fails after
the marker is written, investigate and preserve the failure rather than
automatically retrying and treating test access as if it never occurred.

## What is learned

Ridge combines linear effects and uses regularization to discourage overly large
coefficients. Its product one-hot encoder and numeric scaler are fitted on
training rows only during comparison. The forest combines many decision trees;
it handles nonlinear relationships without scaling. Both use the same explicit
feature list. Product IDs are categories; date metadata and targets cannot enter
the predictor.

All four approaches apply a zero prediction floor. The saved wrapper rejects
missing, nonfinite, negative, or invalid-calendar features and unknown products.
It packages the estimator and learned preprocessing together. Baselines have no
learned numerical coefficients but still use the same input contract.

The recorded candidate configurations are intentionally small: one Ridge and
one forest configuration, not an extensive hyperparameter search. Candidate
order favors simpler methods in numerical ties. Selection uses validation MAE.

## Experiment tracking

MLflow is our local experiment notebook with structured records. SQLite stores
run metadata in `mlflow.db`; model/metric artifacts live in `mlartifacts/`.
No external tracking account or PostgreSQL server is needed at this stage.

Each comparison run logs parameters, train/validation MAE, RMSE and R-squared,
training time, validation batch-prediction time, source checksums, Git revision
and dirty state, dependency versions, and per-product validation results.

Artifacts are explicit joblib bundles plus JSON metadata, logged as ordinary
MLflow artifacts. We use MLflow run IDs as version identifiers; we have not
created Model Registry entries or claimed registered model versions. The final
run links back to the selection run and records held-out test metrics separately.

SQLite-backed local tracking and artifact logging follow the
[MLflow tracking documentation](https://mlflow.org/docs/latest/tracking/).

## Open the dashboard

From the repository root:

```powershell
.\.venv\Scripts\python.exe -m mlflow ui --backend-store-uri sqlite:///mlflow.db --host 127.0.0.1 --port 5000
```

Open http://127.0.0.1:5000 in a browser. Select the
`RetailCast-sales-forecasting` experiment, filter to the
`validation_comparison` phase, select the four runs, and compare
`validation_mae`, `validation_rmse`, and `validation_r2`. Lower MAE/RMSE is better.
The `final_test` run is evaluated with a different fit and on a different period;
do not rank it against validation runs as if their metrics used the same rows.

The dashboard binds only to the local machine. It is not a deployed service.
Training itself does not require a running dashboard server.

## Model files and trust

`models/final/model.joblib` is the serialized model;
`models/final/metadata.json` records its checksum, supported product IDs, feature
order, library versions, provenance, and final metrics. All model files, local
MLflow storage, and row-level prediction outputs are excluded from Git.

Joblib uses pickle-based loading: load only artifacts generated by this trusted
workflow. A checksum identifies bytes but is not a signature and cannot make an
untrusted model safe. The API phase will verify our local bundle consistently.

## Honest interpretation

Training metrics diagnose fit and can be optimistic. Validation decides the
candidate. The final test measures the selected refitted model without changing
the decision afterward. Daily rolling-origin assumptions and correlated target
windows remain as described in `baseline-and-evaluation-plan.md`.

## Learning example

If a forest has much lower training error but worse validation MAE than the
previous-week baseline, choose the baseline. Extra complexity is useful only
when the evidence supports it.
